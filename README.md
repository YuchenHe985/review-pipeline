# Review Pipeline

A reproducible analytics pipeline for marketplace product reviews: contract-checked ingest, point-in-time features in DuckDB SQL, a helpful-vote model with an evaluation that cannot see the future, and reviewer segmentation that is checked for stability. It runs on the public [Amazon Reviews '23](https://amazon-reviews-2023.github.io/) data. The whole Health & Personal Care category (494,121 reviews, 60,293 products) goes from raw files to report in about 45 seconds on an Apple M1 laptop.

This started as a 2026 data-analytics course project: Colab notebooks that sampled 1% of the Electronics reviews with `random.random()`, fit KMeans with k picked from an elbow plot, and fit XGBoost on a random split. In October 2026 it was rebuilt from scratch as a pipeline that a data team could run on a schedule and trust.

## Results (Health & Personal Care, full category)

Full output: [docs/REPORT.md](docs/REPORT.md). It is generated by the pipeline, not typed by hand.

**Question:** when a review is posted, can we tell whether readers will find it helpful, so it can be surfaced early? The test set is the newest 20% of reviews (97,798 reviews from April 2021 on). Only 23.4% of them got any helpful vote.

| model | RMSE | R² (95% CI) | Spearman | helpful share in top 10% | lift |
|---|---:|---:|---:|---:|---:|
| training mean | 0.553 | −0.029 | — | 23.1% | 0.99× |
| ridge, same features | 0.547 | −0.007 [−0.036, 0.019] | 0.237 | 45.1% | 1.93× |
| **XGBoost** | **0.529** | **0.061 [0.051, 0.071]** | **0.281** | **50.0%** | **2.13×** |

- The model's top 10% of new reviews are helpful **2.13 times** as often as average.
- XGBoost beats ridge by +0.067 R² (95% CI [0.044, 0.096], paired bootstrap).
- The absolute R² is low, and that is the honest answer: most helpful-vote variance is not knowable when a review is posted.

**What common shortcuts would have reported** for the same model:

| evaluation design | R² |
|---|---:|
| random 80/20 split (training sees later reviews) | 0.280 |
| time split, plus the catalogue's `average_rating`/`rating_number` (a 2023 snapshot that already counts future reviews) | 0.167 |
| **time split, point-in-time features only (this pipeline)** | **0.061** |

A notebook-style evaluation would have overstated the model by 4.6×. The pipeline refuses to train if a snapshot or target column appears in the feature list.

**Reviewer segments:**
- 18,959 reviewers with at least 2 reviews.
- k = 6, chosen by silhouette (0.348) over k = 2…8.
- The segments are stable across seeds: mean adjusted Rand index 0.997, minimum 0.994.
- Examples: a large group of short 5-star verified reviewers (7,556), a group of detailed reviewers whose reviews draw helpful votes (2,448), a mostly unverified group (2,405) and a photo-reviewer group (1,246).

## Pipeline

```
raw JSONL.gz ──ingest──> typed Parquet + quarantine ──build (DuckDB)──> examples / reviewers ──┬─ train ──> model + metrics
                                                                                               └─ segment ──> segments
                                                                        └──────────── report ──> REPORT.md
```

| Stage | What it guarantees |
|---|---|
| **ingest** | Every line is checked against a data contract (types, ranges, required ids, a timestamp unit check). Rejected lines go to `quarantine.parquet` with their line number and a reason code. The counts always reconcile: read = accepted + quarantined + sampled out. More than 1% rejected stops the run, because a sudden schema change upstream should not quietly become training data. Sampling is deterministic by reviewer (hash of seed and user id), so all of a reviewer's reviews stay together and a rerun picks the same people. |
| **build** | Exact duplicates (same reviewer, item and millisecond) are removed and counted. Product and reviewer history use window frames that end *strictly before* each review (`RANGE … INTERVAL 1 MILLISECOND PRECEDING`), so reviews posted at the same moment never see each other. Missing product metadata is kept as nulls, not dropped. |
| **train** | Time-based split, plus early stopping on the newest slice of the training period. Two baselines (training mean, ridge). Paired-bootstrap 95% intervals. A business metric (helpful share among the top 10%). Feature gain shares. The two leakage diagnostics above. |
| **segment** | Standardized reviewer features. k chosen by silhouette on a fixed sample, Davies-Bouldin reported, and stability measured as ARI across seeds. |

**Reproducibility and operations:**
- **Content-addressed outputs.** Each stage's output id is a hash of its inputs' content, the contract/SQL version and that stage's settings. Rerunning skips finished stages. Changing `[train]` retrains without re-ingesting. A changed source file produces a new batch next to the old one.
- **Atomic publishing.** A stage writes into a staging folder and renames it into place only with a manifest. A crash leaves no half-written output, and the next run sweeps leftover staging folders.
- **Manifests** record input SHA-256s, row counts at every step, the feature list, the settings and the library versions. `requirements.lock` pins the exact versions behind the numbers above.

## Running

```bash
python -m venv .venv && . .venv/bin/activate
pip install -e '.[dev]'
make data           # downloads ~93 MB (CATEGORY=... for another category)
make run            # all stages; writes out/REPORT.md
make test           # tests + coverage
```

Each stage can also run alone: `reviewpipe ingest|build|train|segment|report --config config.toml`.

## Tests

45 pytest tests, all passing. They take about 4 seconds and run on synthetic data, so there is no download. Branch-inclusive coverage is 93%. CI runs them on Python 3.11 and 3.13, with ruff lint and format checks.

- **Contracts:** every broken field maps to its own reason. Seconds-instead-of-milliseconds timestamps are caught. Prices parse "$1,299.99" and treat ranges and junk as unknown.
- **Ingest:** quarantined lines keep their line numbers and the counts reconcile. Too many rejects stop the run and publish nothing. A crash mid-write leaves nothing behind. The same input is reused while a changed input gets a new batch. Sampling keeps whole reviewers and is repeatable.
- **Build:** history excludes the current review, later reviews and reviews from the same millisecond. Duplicates are removed (the most complete copy wins) and counted. Missing metadata is kept. When the window frame is changed to include the current row, two of these tests fail, so they do guard the leakage boundary.
- **Train and segment:** the time split never puts a timestamp on both sides. The model beats the baselines on data with a known signal. A leaky feature list is refused. The bootstrap detects a clearly better model. Segmentation reports k in range and its stability. The report is built from the run outputs.

## Limitations

- One machine and in-memory pandas for training. DuckDB handles the SQL out of core, but a category with tens of millions of reviews would need chunked or distributed training.
- Product price and description come from the 2023 catalogue snapshot and are assumed static. Unlike the rating columns, they do not count reviews, but prices do change over time.
- No scheduler. A stage is a command, so it fits cron, Airflow or a CI job, but none is included.
